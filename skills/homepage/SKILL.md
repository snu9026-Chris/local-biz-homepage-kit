# 홈페이지(제품 웹) 카피 다이어트 스킬

**핵심 한 문장: 각 섹션은 "라벨 + 핵심 타이틀 + 액션(라우팅/CTA)"만으로 자립한다. 나머지 설명은 기본 삭제.**

이건 `visual-design-rules`(격자·정렬·시각)와 **다른 축** — 여기선 **콘텐츠/카피의 정보 다이어트**만 다룬다. 시각 작업이 겹치면 둘 다 로드.

## 0. 대상 구분 (먼저 판정)
- **이 스킬 ✅**: 서비스 홈·앱 메인·대시보드·`/meetup` 같은 **제품 화면의 섹션** (Next.js 컴포넌트 등). 짧고 스캔되는 UI.
- **이 스킬 ❌**: 긴 스크롤 **홍보/수업소개서 랜딩** → `class-intro-page` 스킬. (거긴 스토리·설득 카피가 본체라 규칙이 다름)

## 0.5 ⛔ 절대 규칙 — 섹션 타이틀 밑 부연설명은 **쓰지 마라** (2026-07-28 재확정, 반복 지적)

**`<h2>타이틀</h2>` 바로 밑에 회색 한 줄 설명을 붙이는 습관 = 이 스킬 최대 위반.** Chris가 볼 때마다 지적한다.

- 실패 예시(전부 삭제 대상): `가장 빠른 수업` 밑 "지금 신청 가능한 2회차입니다" / `수강생 후기` 밑 "수업이 끝나고 오픈채팅에 남겨주신 말들입니다" / `신청 전에 많이 묻는 것` 밑 "여기서 답이 안 나오면 오픈채팅으로 물어보세요" / 사진 갤러리 밑 캡션 "매주 열리는 실제 수업 현장입니다".
- **왜 매번 재발하나**: 만들 때는 "친절해 보여서" 붙이게 된다. 하지만 **타이틀이 이미 그 말을 했고**, 바로 아래 카드/콘텐츠가 나머지를 증명한다. 부연은 정보가 아니라 **노이즈**다.
- **새 섹션을 만들 때마다 자문**: "타이틀 + 콘텐츠만으로 뜻이 통하나?" → 통하면 부연 삭제. 안 통하면 **부연을 붙이지 말고 타이틀을 고쳐라.**
- 예외는 딱 하나 — **오해하면 손해 보는 조건**(환불·마감시각·필수 준비물 등). 이건 부연이 아니라 **경고**라서 남긴다.
- 삭제 후 제거된 요소의 `margin`을 인접 요소로 넘겨 세로 리듬이 깨지지 않게 할 것.

## 1. 섹션 구성 최소 골격
한 섹션에 남기는 것은 원칙적으로 이 3개뿐:
1. **라벨/eyebrow** (예: `OFFLINE MEETUP`) — 이 섹션이 뭔지 한 단어
2. **핵심 타이틀** (예: `지금 모집 중인 수업`) — 이 섹션의 단 하나의 메시지
3. **액션** — 라우팅 링크/버튼 (예: `전체 일정 ›`) 또는 실제 콘텐츠(카드 리스트)

## 2. 기본 삭제 대상 (강하게 정당화될 때만 살림)
- **부가 설명 서브텍스트** — 타이틀 밑에 붙는 "어디서·얼마·어떻게" 안내. (예: "서울대입구역 오프라인 강의 · 수강료는 카드에서 확인" ← 삭제)
- **디테일을 상위 카피에 중복 노출** — 위치·가격·조건·정원 등은 **실제 데이터 카드/상세에서 자연히 보임**. 섹션 카피로 미리 설명하지 말 것.
- "~에서 확인하세요" / "자세한 내용은 아래" 류 **안내 문구** — 레이아웃 순서가 이미 안내다.
- 타이틀과 거의 같은 말 반복하는 subtitle.

## 3. 판정 체크리스트 (문장마다 물어라)
> 일반 부연 검사는 `visual-design-rules` §A3. 여기 둘은 **제품 웹 고유**다.
- [ ] 섹션이 **라벨+타이틀+액션만으로 자립**하는가? → 그게 목표 상태.
- [ ] 삭제 후 **간격**(제거된 요소의 margin)을 인접 요소로 넘겨 레이아웃 안 깨지게 했는가?

## 4. 함정
- 서브텍스트를 지우면 그 요소의 `margin-bottom`이 같이 사라져 **다음 블록이 붙는다** → 타이틀(또는 위 요소)에 그 하단 여백을 넘겨줄 것.
- "정보를 줄이면 불친절"이라는 유혹 — 제품 홈에선 **덜어낸 게 더 친절하다**(스캔성). 디테일이 필요하면 그건 클릭 후 상세에서.

## 5. 원칙 (왜)
사용자(Chris)는 홈에서 **군더더기 카피를 극도로 싫어한다.** "핵심 메시지만." 지역·수강료·안내문 같은 걸 홈 섹션 헤더에 넣으면 반드시 지적당한다. 처음부터 3-요소 골격으로 짜라.

추가 다이어트 대상 (2026-07-23 확정):
- **조건 서브텍스트** ("최소 N명 모집 시 진행 · 정원 · 예약금") — 홈/목록 헤더에서 삭제, 신청 팝업에서만 안내. 대신 남긴 타이틀은 **한 단계 키운다** (모바일 22→26px급).
- **종료/과거 아이템 리스트** ("종료된 강의", "지난 강의") — 일반 사용자 화면에서 기본 숨김. 기록 열람이 필요한 admin PC 뷰에서만.

추가 다이어트 대상 (2026-07-22 확정):
- **삭제 vs 대체 판단**: 필러를 지운 자리에 그 섹션의 "다음 행동"이 필요하면 삭제 대신 **액션 라인 1개**로 압축. 예: 조건 서브텍스트(정원·예약금) → **"강의에 대한 모든 문의는 [오픈챗](KAKAO_OPEN_URL 링크)에서 해주세요"** 한 줄. 여러 줄 안내 나열 ❌ → 링크 걸린 한 문장 ✅.
- **같은 필러는 라우트 간 복붙됨 → grep 일괄**: 동일 서브텍스트가 홈(`app/page.tsx`)·목록(`/meetup`)·모바일 셸에 중복인 경우 많음. 한 곳 고치면 **그 문구를 grep으로 전부 찾아 함께** 정리. `!isMobile`로 한쪽만 숨긴 분기도 확인 — 모바일에선 안 보일 뿐 소스엔 남아있다. 문구 삭제로 unused된 import(예: `DEPOSIT`)까지 정리 + `tsc --noEmit` 통과 확인.

## 6. 모바일(iOS) 셸 함정 — 홈/제품 웹 작업 시 회피 체크 (2026-07-23)
Next.js 모바일 웹 셸 작업에서 반복 확인된 iOS 전용 함정. 상세 원인·커밋은 tutoring-session `errorfix.md` 2026-07-23 항목 참조.
- **뷰포트**: body는 `100dvh`(100vh는 iOS 큰 뷰포트라 하단 갭/상단 잘림). `viewport-fit=cover` 켰으면 고정 헤더에 `safe-area-inset-top` 패딩 필수.
- **키보드**: `interactive-widget=resizes-content`는 **안드로이드 전용**. iOS는 visualViewport로 키보드 높이 + **밀림 오프셋(vv.pageTop)** 둘 다 셸 한 곳에서 핀닝(`높이 차감 + translateY(pageTop)`). 페이지별 키보드 핸들러 중복 금지 — 갭 제조기.
- **자동 링크 밑줄**: 계좌번호·이메일 노출 페이지는 `formatDetection: { telephone/email/address: false }` 기본.
- **검증**: iOS 전용 증상(키보드·밑줄·뷰포트 밀림)은 데스크탑 responsive 모드로 재현 불가 — **실기기 확인 필수**.

## 7. 완성 후 콘솔 QA (런타임 에러 사전 검증)
홈/제품 웹을 손댔으면 배포 전 **콘솔 런타임 에러를 헤드리스로 미리 잡는다** (F12 육안 대신 자동).
- 도구: `gstack browse` (가벼움) 또는 `qa` (플로우 조작까지). 바이너리 직접: `~/.claude/skills/gstack/browse/dist/browse`.
- 최소 절차: `$B viewport 390x844` → `$B goto <url>` → **`$B console --errors`** (+ 필요시 `$B network` 실패요청).
- **함정 — 확장프로그램발 에러를 우리 버그로 오인 금지**: 실제 크롬(사용자 F12)엔 확장이 주입한 에러가 섞인다. 헤드리스 browse는 **확장이 없어** 우리 코드 에러만 나온다 → 둘을 비교해 출처 판별.
  - 확장발 시그니처(무시): `chrome-extension://...` 경로 · `"A listener indicated an asynchronous response ... message channel closed"` · Adobe(`efaidnbmnnnibpcajpcglclefindmkaj`) 폰트 인터벤션. 이런 건 **우리가 고칠 게 없다.**
  - 헤드리스에서 `(no console errors)`면 우리 코드는 클린 — 사용자 콘솔 노이즈는 확장 탓이라고 안내.
- 실제 사례(2026-07-22): 홈 콘솔의 "message channel closed" 2건 = Adobe Acrobat 확장. 헤드리스 browse 로드 시 에러 0 → 우리 코드 무결 확인.
- **배포 후 라이브 확인**: 카피/UI 변경은 푸시 후 Vercel 반영을 browse로 어서트 — `$B viewport 1280x800` → `$B goto <라이브URL>` → 새 문구 present / 옛 문구 gone. **반드시 데스크탑 뷰포트로**: 모바일 뷰포트는 `!isMobile`로 숨긴 요소 탓에 신·구 판별이 오판된다(구버전에서도 안 보여 "제거됨"으로 착각).

## 8. 모바일 카드·워딩·UI 디테일 (2026-07-23 세션 누적 — Chris 확정 패턴)

### 워딩 축약 (모바일 카드)
- **수식어 제거 축약형**: "입문자를 위한 클로드 원데이 클래스" → "클로드 원데이 클래스 초급". 데이터에 `shortLabel` 필드를 두고 `isMobile ? shortLabel ?? label : label` — 잘리는 말줄임(…)이 보이면 축약형 미지정 신호.
- **장소/주소 접미어 삭제**: "서울대입구역 스터디룸" → "서울대입구역" (`placeShort` 헬퍼). 카드 한 줄에 안 들어가는 정보는 접미어부터 깎는다.
- 상태 문구도 축약: "마감되었습니다" → "마감", "수업 소개서 보기" → "수업소개서".

### 버튼/CTA
- **2-up 한 줄 버튼**: 주 CTA(신청)와 보조 CTA(소개서)는 가로 반반 한 줄 — 세로 스택보다 카드 높이 절반.
- **CTA 색 = 항목 브랜드 색**: 신청 버튼은 노랑 고정색이 아니라 그 트랙/아이템의 로고 색(meta.color) + 흰 글씨.
- 텍스트만 있는 액션 링크("전체 일정 ›")는 **필(pill) 배지 스타일로 승격** — 페이지 eyebrow 배지와 같은 톤으로 통일.

### 아이콘 톤 ("AI스럽다" 지적 회피)
- **이모지 UI 아이콘 금지**: 📷/➤/📲 같은 이모지 버튼 → SVG 스트로크 아이콘(카메라·종이비행기 등)으로. 이모지는 콘텐츠 라벨에만.
- ⭐ **타사 브랜드 로고(인스타·유튜브·카카오·구글…)는 손으로 그리지 말고 공식 마크를 검색해 가져온다.** `curl -s https://raw.githubusercontent.com/simple-icons/simple-icons/master/icons/<brand>.svg` → 24×24 채움 path를 상수로 박고 `fill`만 준다. stroke로 근사해 그리면 18~20px에서 곡선이 깨져("삐쭉하다") 반드시 지적당한다. 브랜드 색·그라데이션 방향도 검색값 준수(인스타 = 좌하단 radial). 상세 절차는 visual-design-rules §C3.
- **소셜 채널 버튼 묶음**: 브랜드 색 원형(36px) + 흰/검정 글리프로 통일하고, 글자 라벨은 주 액션(로그인 등) 하나만 남긴다 — 색 원이 3~4개 나열되면 라벨까지 붙일 필요가 없다.
- **아이콘 중복 금지**: 한 행에 앱 아이콘 이미지 + 이모지 2개 ❌ — 메인 아이콘 하나만.
- 전송류 버튼은 **입력 있을 때만 활성색**, 빈 상태는 회색 (iMessage 패턴).
- 아이콘 버튼(뒤로가기 등)은 **38px+ 원형 터치 타깃** (텍스트 ‹ 금지).

### 리스트/카드 구조
- 일정 리스트는 **주(월~일) 그룹핑** — "이번 주/다음 주" 헤더, 오늘 기준 자동 롤오버.
- 모바일에서 넓은 표(4컬럼+)는 **2단 스택 카드**로: 1행 아이콘+제목+메타(ellipsis) / 2행 뱃지+버튼(no-wrap).
- eyebrow 배지가 섹션 라벨을 겸하면 **배지↔헤딩 간격을 타이트하게** (mt-8 → mt-3.5급).

### 프로필/호스트 카드
- **한 정보는 한 곳에만**: 학력·경력은 이름 밑, 핵심 어필(500억)은 강조 박스, 평점은 카드 안 뱃지 — 카드 밖 통계 칩과 중복 배치 금지.
- 잔챙이 통계 칩 행은 카드 안으로 흡수하고 삭제 (★4.9는 카드 우상단 필 뱃지).

## 9. 강의 뷰어·허브 모바일 표준 (2026-07-26 Chris 확정 — tutoring-session 적용·검증 완료)

새 강의 트랙을 추가하거나 뷰어/허브를 만들 땐 아래 두 패턴이 표준. 임의로 다른 방식 쓰지 말 것.

### 슬라이드 덱 뷰어 = 비율 유지 축소 (ScaledSlideFrame)

## 10. Supabase 보안 잠금 — 커스텀 인증(localStorage) 사이트의 PII 보호 (2026-07-27 Chris 확정·실서버 검증)

> **트리거**: "보안 감사 조치", "회원/신청 데이터 안전한가", "anon 키로 다 읽힌다", "RLS 잠가", "관리자 비번이 번들에 노출". cso 감사 후 CRITICAL/HIGH 조치 시.

**전제(이 프로젝트의 핵심 함정)**: 이 사이트는 Supabase Auth가 아니라 **localStorage 커스텀 인증** → 관리자든 학생이든 DB엔 전부 `anon` 롤이다. 그래서 **RLS로 "관리자만" 같은 구분이 원천적으로 불가** → 서버 라우트 + DEFINER RPC로 우회 설계해야 한다. anon 키·URL은 `supabase.ts`에 **하드코딩 폴백**으로 박혀 있어 공개(정상, anon은 공개키). 진짜 비밀(관리자 비번·service_role)만 서버로 빼는 게 목표.

**설계 원칙 — 무엇을 어디로 보내나**:
- **관리자 비번**: 클라 비교(`NEXT_PUBLIC_*`) 금지 → `/api/admin/login`에서 서버 env(`ADMIN_PW`)로만 비교. 성공 시 **httpOnly 서명 쿠키**(HMAC of ADMIN_PW, 7일 만료) 발급 = 이후 관리자 API 인증 근거. (`src/lib/adminAuth.ts`)
- **관리자 읽기/쓰기**(회원목록·등급·신청자·승인·삭제·사진purge·명단·강퇴): `/api/admin/data` 단일 라우트(action 스위치) — 쿠키 검증 후 **service_role 클라이언트**로 RLS 우회. (`src/lib/supabaseAdmin.ts` — 반드시 지연 생성 `getSupabaseAdmin()`, URL은 supabase.ts와 동일 폴백)
- **학생 본인 조회**(등급 게이트·내 신청): 클라 유지하되 **DEFINER RPC**로 — `get_grade(email)`, `my_applications(code,name)`. 소유자=postgres·`force_rls=false` 확인되면 DEFINER가 RLS 우회함(사전 `pg_class.relforcerowsecurity` 체크 필수).
- **비관리자 degrade**: 관리자 API는 401 → 클라 헬퍼(`adminClient.ts`)가 null→빈배열 반환. 학생 화면이 안 깨지게.

**RLS 잠금 자체 (맨 마지막·핵심 함정)**:
- **PII 테이블만 잠근다**: `members`(정책 전부 제거=완전 차단), `class_applications`(INSERT만 `to public` 유지, SELECT/UPDATE/DELETE 제거).
- **`classes`는 절대 안 건드린다** — PII 없음 + **신청 트리거(`check_capacity`/`bump_seat`)가 anon으로 classes를 SELECT/UPDATE함** → classes 쓰기 잠그면 신청 INSERT가 깨진다. (트리거가 class_applications는 안 건드리므로 그쪽 SELECT 잠금은 신청에 무해 — 이걸 트리거 본문으로 먼저 확인.)
- **신청 INSERT는 readback(.select) 없음** → SELECT 잠가도 신청 정상. 이걸 코드로 먼저 확인.

**배포 순서 (무중단·롤백 안전 — 반드시 이 순서)**:
1. DEFINER RPC 먼저 생성(추가 전용, 동작 불변) → SQL로 실동작 검증.
2. 서버 라우트·클라 리와이어 코드 배포 (이때 RLS는 **아직 공개** → 안 깨짐).
3. env 세팅: `ADMIN_PW`, `SUPABASE_SERVICE_ROLE_KEY`(Supabase 대시보드 Settings→API Keys→service_role secret). **Vercel은 env 추가만으론 반영 안 됨 → 재배포 필수**(빈 커밋/푸시). CLI: `printf '%s' '값' | vercel env add NAME production`. service_role은 sensitive라 CLI/대시보드로 재조회 불가.
4. 실서버 검증(RLS 공개 상태): 관리자 로그인+쿠키, 관리자 데이터 라우트(service_role 동작), **비인증 401**, 학생 RPC(anon), 신청 INSERT.
5. **마지막에** RLS 잠금 마이그레이션 적용. 롤백 SQL을 마이그레이션 주석에 박아둔다(`create policy ... using(true)` 2줄).
6. 잠근 뒤 재검증: anon 직접 SELECT가 `[]`로 차단 / RPC·신청 여전히 200 / 신청 INSERT E2E(테스트행 삽입→삭제, seat 드리프트 0 확인) / 관리자 신청현황 조회.

**남은 갭(다음 라운드 후보)**: `/api/admin/login` **rate-limit 없음**(브루트포스) / 관리자 비번 8자 중간강도 / 관리자 비번 self-change는 env로는 불가(런타임 env 못 고침 → DB 저장 방식으로 전환해야 자체 변경 가능) / MEDIUM: `NEXT_PUBLIC_VSIX_PW`, public bucket listing, leaked-password-protection.

**근본 해결(권장 방향)**: 커스텀 localStorage 인증 → **Supabase Auth(OAuth 구글/카카오)**로 이전하면 `auth.uid()` 기반 RLS가 정상 작동 → 위 우회 설계 상당 부분 불필요해짐. 단 대규모 마이그레이션. → **§11에서 실행 완료(2026-07-27).**

## 13. 같은 카테고리는 한 곳만 고치지 마라 — 나머지도 바꿀지 **먼저 묻는다** (2026-07-29 Chris 확정, 반복 지적)

같은 종류의 UI(수업 카드 · 트랙 아이콘 타일 · 버튼쌍 · 리스트 행 · 섹션 타이틀 …)를 **한 화면에서 바꿨으면,
같은 종류가 쓰이는 다른 화면도 전부 찾아서 "여기도 같이 바꿀까요?"를 묻고 시작한다.**
한 곳만 바꿔 놓으면 화면마다 같은 요소가 다르게 생겨 반드시 지적당한다.

**작업 순서 (고정)**
1. 바꾼 요소의 **카테고리 이름**을 정한다(예: "수업 카드", "트랙 아이콘 타일").
2. `grep`으로 **그 카테고리가 렌더되는 모든 지점**을 뽑는다 — PC/모바일, 홈/목록/상세/모달/채팅 전부.
3. 목록을 그대로 보여주고 **"전부 바꿀까요 / 여기만 둘까요"를 묻는다.** (묻지 않고 전부 바꾸는 것도 금지 — 스코프 침범)
4. 승인 후 일괄 반영 → 다시 `grep`으로 옛 형태 0건 확인.

**전형적 누락 지점** (매번 여기서 빠진다)
- 모바일 전용 컴포넌트(`components/mobile/*`)가 PC와 따로 구현돼 있어 한쪽만 바뀜
- 목록 카드는 고쳤는데 **채팅방 목록·마이페이지·관리 콘솔**의 같은 카드가 남음
- 카탈로그/그리드 타일 vs 일정 카드 타일이 서로 다른 코드
- 팝업(신청 모달·소개서 뷰어) 안의 같은 요소

**근본 예방**: 같은 카테고리는 **공용 컴포넌트 1개**로 뽑아 전 지점이 import한다(예: `TrackTile`).
인라인 복붙이 남아 있으면 다음에 또 갈라진다. §12(브랜드 마크 전 지점 교체)와 같은 원리.

## 14. 셸 서피스 = 아이보리 명도 계단 (tonal ladder) — 흰색 나열 금지 (2026-07-29 Chris 확정·unitas.kr 검증)

헤더·사이드바·본문을 전부 흰색으로 두면 경계가 사라지고, 반대로 회색(#e9e9ed)을 남기면
"안 칠한 자리"로 읽힌다(둘 다 지적당함). **같은 색상(웜 아이보리)에서 밝기만 단계로 나눈다.**

```
헤더      --iv-header  #f0ead9   가장 짙음 (위에서 아래로 옅어진다)
사이드바   --iv-nav     #f7f3e8   모바일 하단 탭바도 같은 층(둘 다 내비게이션)
본문      --iv-content #fdfcf7   가장 옅음
카드      #ffffff                가장 옅은 본문 위에서 한 단 떠 보인다
경계선    --iv-line    #e8e2d2
```

- **토큰은 globals.css `:root` 한 곳에만.** 컴포넌트는 `var(--iv-*)`만 참조 — 값이 흩어지면 계단이 어긋난다.
- **깊이는 얕게.** 그림자를 키우면 다시 "떠 있는 패널"이 되고, 없앤 여백 문제가 재발한다.
  상단 1px 하이라이트 + 경계에 아주 옅은 그림자면 충분.
- **⛔ 반투명 서피스 금지** — `rgba(...)` 배경은 아래 계단이 그대로 비쳐 그 면이 아이보리로 물든다.
  (실제 사고: 헤더 로고 타일 `rgba(118,118,128,.10)` → 헤더 아이보리가 비쳐 흰 타일이 상아색으로 보임.)
  계단 위에 얹는 타일·칩은 **불투명**으로.
- **페이지 래퍼가 계단을 덮는다.** 각 페이지가 `background:'#fff'`나 `linear-gradient(#fff,#fafaf7)`를
  자기 루트에 걸어두면 본문 단이 무력화된다 → 페이지 래퍼도 `var(--iv-content)`로 통일할 것.
  (홈·모바일홈·목록·채팅·마이·강의 전부 각자 칠하고 있었다.)
- **브랜드 색은 예외** — 구글 4색·카카오 노랑·인스타 그라디언트·유튜브 빨강은 원래 색 유지.

**적용 후 검수 (육안 금지 — §7과 함께)**
1. 서빙되는 CSS를 받아 토큰 존재 확인: 없으면 코드가 아니라 **번들러 캐시** 문제(errorfix 참조).
2. 렌더 스크린샷에서 **세 면의 픽셀을 직접 샘플링**해 의도한 hex와 대조.
   `PIL: im.getpixel((x,y))` — 헤더/내비/본문 각 1점이면 계단이 섰는지 즉시 판정된다.
3. 미정의 `var()`는 배경을 **투명**으로 만들어 뒤 레이어가 비친다 → "색이 안 먹네"로 오진하기 쉽다.

## 15. 링크 프리뷰 카드(OG)는 홈페이지 "구성 요소"다 — 초기 디자인 단계에서 같이 결정 (2026-07-30 Chris 확정)

**홈페이지를 만들 때 OG 카드 디자인을 반드시 같이 결정한다.** 지금까지처럼 나중에 지적받고 고치지 말 것.
카톡·인스타 DM·슬랙으로 링크를 공유하는 순간 **잠재 수강생이 사이트보다 먼저 보는 화면**이 이 카드다.
사실상 사이트의 첫 인상이자 대문인데, 개발 산출물 목록에서 빠지기 쉬워 방치된다.

### 홈페이지 작업 시작 시 함께 정할 것 (히어로 디자인과 같은 위계로 다룬다)
- **이미지**: 브랜드 마스코트/로고 + 워드마크. 히어로와 톤·마스코트가 일치해야 한다(§12 전 지점 일괄 교체 대상에 OG도 포함).
- **og:title / og:description**: 사이트 `<title>`을 그대로 재활용하지 말 것. 카드는 **처음 보는 사람에게 소구하는 한 줄**이어야 한다(청자 관점).
- **도메인**: `og:url`·`metadataBase`는 반드시 **정식 도메인**. vercel 임시 URL이 남아 카드 하단에 노출되는 사고가 실제로 있었다.

### 규격 — 잘림 방지가 최우선
- **1200×630 (1.91:1) 고정.** 정사각형 금지 — 카톡이 가로로 크롭해 **위아래가 잘린다**(2160×2160으로 만들어 실제로 잘렸음).
- **안전영역**: 콘텐츠를 상하 **90px 이상** 안쪽에 둔다 → 플랫폼이 2:1·16:9로 더 크롭해도 생존.
- 검수는 눈대중 금지 — **콘텐츠 bbox를 픽셀로 측정**해 각 비율 크롭 박스 안에 들어오는지 계산으로 확인. 카톡 실제 표시 폭(**약 330px**)으로 축소해 글자 가독성도 확인.

### 함정
- **배경색 = 마스코트에 든 "배경과 같아야 하는 색"과 일치시켜라.** 픽셀 마스코트의 흰 캡(cap)처럼 원래 배경에 묻히도록 설계된 색이 있으면, 배경이 다르면 그 픽셀이 **흰 박스처럼 드러난다**. 하드코딩 말고 마스코트 데이터의 색 상수를 그대로 배경에 쓴다.
- **이미지 자산을 손으로 만들지 말고 생성 스크립트로 만든다.** 손으로 만든 og.png는 마스코트를 교체한 뒤에도 **옛 마스코트가 그대로 남았다**(앱 아이콘만 갱신됨). 마스코트 데이터를 읽어 그리는 스크립트를 두면 재생성 한 번으로 끝난다.

### 캐시 — "코드는 맞는데 카톡은 옛것" 의 정체
- **캐시 무효화는 쿼리(`?v=2`)가 아니라 파일명(`og-v2.png`)으로 한다.** 카톡 스크래퍼가 쿼리 붙은 og:image를 제대로 못 가져오는 사례가 있다.
- 교체 후 **카카오 개발자 > 도구 > 카카오톡 URL 메타정보 관리**에서 `디버그`로 현재 스크랩 값 확인 → `캐시 초기화`.
- ★ **카톡은 URL 문자열 단위로 캐싱한다.** `https://도메인`만 초기화하면 `http://도메인`·`도메인/`(trailing slash)·`www.` 는 **별개 엔트리로 옛 카드가 남는다.** 변형 전부 초기화.
- ★ **이미 전송된 메시지의 카드는 절대 안 바뀐다.** 확인은 반드시 **새 메시지**로. 즉시 확인하려면 카톡이 한 번도 본 적 없는 주소(`https://도메인/?x=1`)로 보내면 새 카드가 바로 뜬다(카드 하단 도메인 표기는 그대로).
- **디버거에 새 카드가 뜨면 우리 쪽 작업은 끝난 것이다.** 그 이후 지연은 카톡 캐시 TTL이라 코드로 손댈 게 없다 — 더 고치지 말고 기다리거나 URL 변형 초기화로 대응.

## 16. 모바일은 «축소»가 아니라 «구조 교체» (2026-08-15 Chris 확정 — chiyounglee.com 배포 검증)

> **트리거**: "모바일로도 만들어줘", "PC 꾸겨넣은 것 같다", "모바일은 최대한 길면 안 되고 깔끔해야 해", 폰 스크린샷을 주며 지적할 때.

**이번 세션에서 같은 지적을 6번 받았다.** 매번 폰트·패딩을 깎아서 냈고 매번 "PC 꾸겨넣었다"는 답이 돌아왔다.
원인은 명확하다 — **데스크톱 구조를 유지한 채 크기만 줄였기 때문.** 반응형 리플로우는 모바일 설계가 아니다.

### 판정 — "꾸겨넣었다"의 신호
- 데스크톱에 있던 요소가 **개수 그대로** 모바일에 있다(필터 칩 6개 → 가로 스크롤 6개).
- 한 항목의 정보량이 데스크톱과 같다(제목+저자+저널+태그3+링크).
- 화면 폭에 안 맞아 **어절 중간에서 꺾인 줄바꿈**이 보인다.
- 요소 오른쪽에 **큰 빈 공간**이 있다(세로로 쌓기만 해서 생김).

### 대응 — 줄이지 말고 «바꾼다»
| 데스크톱 | 모바일 | 왜 |
|---|---|---|
| 칩 필터 여러 줄 | **타일 그리드(단일 선택)** | 칩은 가로 스크롤로 바꿔도 결국 PC UI. 타일은 «필터 + 요약»을 겸한다 |
| 전 그룹을 N개씩 나열 | **선택된 «한 그룹»만 렌더** | 9개 그룹 × 2개 = 결국 긴 페이지. 나머지 그룹은 화면에 «없어야» 한다 |
| 전체 목록 | 그룹당 2건 + **펼치기/접기 쌍** | 펼치기만 있으면 되돌릴 길이 없다 — 접기는 옵션이 아니다 |
| 항목의 모든 메타 | **역할 1개 + 출처 1줄 + 아이콘 링크** | 부제 URL(`scholar.google.com`)·분야 pill은 라벨과 같은 말 |
| 긴 제목 전체 | **2줄 클램프 + 탭하면 펼침** | |
| 아바타 위 / 이름 아래 | **아바타 «옆»에 이름** | 세로로 쌓으면 아바타 오른쪽이 통째로 빈다 |
| 상단 액션 버튼 + 하단 연락처 카드 | **하나만 남기고 섹션 순서 재배치** | 중복 제거가 축소보다 효과가 크다 |

**섹션 순서도 모바일에서 다시 짠다.** 데스크톱 «본문 + 우측 레일» DOM을 그대로 쌓으면 레일 내용(지표·연락처)이 맨 아래로 밀린다.
→ `.wrapper, .rail { display: contents }` 로 해체해 상위 flex 의 직계로 올린 뒤 `order` 로 재배열.
순서 기준은 «판단이 서는 순서»: 정체 → 핵심 숫자 → 근거 → 상세 목록 → 연락.

### ⚠ 함정 (전부 이번에 실제로 밟았다)
- **`align-items:start` 의 축이 뒤바뀐다.** grid 에서는 «세로» 정렬인데 모바일에서 세로 flex 로 바꾸는 순간 «가로» 정렬이 된다
  → 내용이 좁은 카드만 폭이 쪼그라든다. **grid → column flex 전환 시 `align-items:stretch` 를 반드시 명시.**
- **grid 컨테이너의 absolute 자식은 `place-items` 를 받아 shrink-to-fit 된다.** `inset:0` 을 네 방향 다 줘도 소용없다
  → 빈 `<span>` 배경 레이어가 0×0 이 되어 **배경 이미지가 통째로 안 보인다.** 배경은 `<img>` + `width/height:100%` 로.
- **브레이크포인트를 넘나들면 렌더 모드를 다시 계산해야 한다.** `resize` 에서 폰트만 갱신하고 `render()` 를 안 부르면
  태블릿 회전 시 62편 중 2편만 남거나, 필터 UI 없이 전부 펼쳐진다.
- **`hidden` 속성은 클래스의 `display` 를 못 이긴다** → `[hidden]{display:none!important}` 를 전역에 두거나 클래스로 숨겨라.
- **0건 분기보다 «먼저»** 부수 UI(타일·필터)를 숨겨라. `return` 뒤에 두면 "결과 없음" 위에 타일이 그대로 남는다.
- **검색 중에는 그룹 필터를 끈다.** 안 그러면 다른 그룹의 항목을 검색했을 때 "결과 없음"처럼 보인다.
- **숫자·범위를 손으로 적지 마라.** "37편(60%)"·"2024–2026" 이 실제 데이터(38편 61%, 2025–2026)와 어긋난 채 배포될 뻔했다 → **데이터에서 계산.**

### 검증 (브라우저 없이도 가능)
헤드리스가 죽어도 이 둘은 항상 돌아간다 — 손대고 나면 매번 실행:
- **태그 짝 검사**: python `html.parser` 로 열림/닫힘 스택 대조 (구조 붕괴 즉시 발견)
- **JS 구문 검사**: node `new Function(script본문)` (템플릿 문자열 오타·괄호 누락)
- 데이터 정합: 화면에 박힌 숫자를 원본 배열로 재계산해 대조

## 17. UI 문구 4원칙 — «어떻게 쓰나» (2026-08-22 도입 · anthropics/skills `frontend-design`)

§0.5~§3 이 «얼마나 쓰나»(다이어트)라면 이건 «어떻게 쓰나»다. **축이 달라 둘 다 적용한다.**

**① 능동태 — 눌렀을 때 벌어지는 일을 그대로 적는다**
- ❌ 「제출」 · 「확인」 → ⭕ 「신청 저장」 · 「결제하기」
- 버튼 이름이 동작을 말하지 않으면 사용자는 누르기 전에 멈춘다.

**② 이름은 흐름 전체에서 한 번 정하면 끝**
- 「신청」 버튼을 눌렀으면 완료 문구도 **「신청됐습니다」**. 중간에 «접수»·«등록»으로 갈아타지 않는다.
- **화면 · 메일 · 알림톡이 같은 단어**를 써야 한다.
  ⚠ 이 저장소는 같은 기능이 PC · 모바일 · 서버 · 메일에 여러 벌 있어 **여기서 가장 잘 갈린다** →
  문구를 바꾸면 `FEATURES.md` 그 기능의 「면」 목록을 열어 전부 맞춘다.

**③ 에러는 사과하지 말고 «다음 행동»을 말한다**
- ❌ 「죄송합니다. 오류가 발생했습니다.」 — 무슨 일인지도, 뭘 할지도 없다
- ⭕ 「카드 승인이 거절됐습니다. 다른 카드로 다시 시도해 주세요.」
- 서비스의 목소리로 쓴다. 사람이 미안해하는 말투가 아니다. **모호한 에러는 문의를 만든다.**

**④ 빈 화면은 «비었다»가 아니라 «시작하라»**
- ❌ 「신청 내역이 없습니다.」 → ⭕ 「아직 신청한 수업이 없습니다. 일정에서 골라보세요.」 + 버튼

**공통 둘**
- **사용자가 조작하는 이름**으로 부른다 — 「알림 설정」 ⭕ / 「웹훅 설정」 ❌ (시스템 구현 용어 금지)
- **한 요소는 한 가지 일만** — 라벨은 이름표, 예시는 예시. 하나가 조용히 둘을 겸하지 않는다.
